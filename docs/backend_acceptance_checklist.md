# Чек-лист приёмки BuildTrack Backend

Этот чек-лист закрывает только этап backend из согласованной сметы. В него не входят
дашборд, интеграция с дроном/LiDAR, BIM/3D, Solana, инфраструктура и массовая
оцифровка российских строительных нормативов.

## Среда приёмки

1. Установить зависимости из `requirements.txt`.
2. Задать собственное значение `BUILDTRACK_JWT_SECRET`.
3. Выполнить `alembic upgrade head`.
4. Запустить `uvicorn app.main:app`.
5. Открыть `/docs` и проверить, что `/health` возвращает `status=ok`.

## Первый администратор

На новой базе один раз вызвать `POST /auth/bootstrap`, указав электронную почту,
ФИО и пароль не короче восьми символов. Через `POST /auth/login` получить Bearer
токен и авторизовать Swagger. Повторная первичная настройка должна вернуть HTTP 409.

## Сквозной сценарий приёмки

1. Создать проект.
2. Создать этап строительства.
3. Создать прораба, инспектора, рабочего и инвестора.
4. Добавить пользователей в проект и назначить роли.
5. Создать активные учебные нормативные правила для этапа.
6. Загрузить PDF и проверить SHA-256 и относительный ключ хранения.
7. Запустить проверку документа.
8. Убедиться, что проверка сохранила точный хеш документа и снимки версий правил.
9. Рассмотреть каждое открытое замечание и проверить его историю.
10. От имени прораба создать задачу и назначить рабочему.
11. От имени рабочего открыть назначенную задачу, начать и отправить на проверку.
12. От имени прораба или инспектора принять или отклонить результат.
13. Скачать отчёты проверки в JSON и PDF.
14. Создать технический акт приёмки этапа.
15. Провести акт по цепочке `draft -> ready -> approved` от имени прораба или инспектора.
16. Проверить снимки участников и замечаний, хеши и историю акта.

## Обязательные отрицательные проверки

- Неавторизованный бизнес-запрос возвращает HTTP 401.
- Повторная первичная настройка администратора возвращает HTTP 409.
- Поддельный PDF или неверное расширение возвращает HTTP 400.
- Слишком большой PDF возвращает HTTP 413.
- Этап из другого проекта возвращает HTTP 409.
- Проверка без активных правил этапа возвращает HTTP 409.
- Новую версию документа или правила нельзя создавать от неактивной версии.
- Недопустимый переход статуса задачи, замечания или акта возвращает HTTP 409.
- Рабочий не видит чужую задачу и не меняет её реквизиты.
- Рабочий не подтверждает собственный результат и не действует от имени другого пользователя.
- Инвестор просматривает задачи, но не изменяет их и не назначается исполнителем.
- Акт приёмки этапа с нерассмотренными замечаниями не переходит в `ready`.
- Старый JWT перестаёт работать после смены пароля или деактивации пользователя.

## Правило для учебных данных

Коды `BT-TEST-*` и учебный PDF являются только данными для проверки программы. Их
нельзя представлять как ГОСТ, СП, СНиП, строительную экспертизу или юридически
значимый результат приёмки. Признак `is_demo` сохранён как техническое поле API для
безопасного отделения учебных правил от подтверждённой нормативной базы.

## Подтверждения, формируемые автоматическими тестами

- Миграции Alembic с пустой базы до текущей версии.
- Запуск API и формирование OpenAPI.
- Загрузка, хеширование, скачивание и версионирование PDF, отклонение неверного типа и размера.
- Неизменяемые снимки нормативных правил внутри проверки.
- Детерминированные замечания и журнал ручного рассмотрения.
- Формирование отчётов JSON/PDF и повторное открытие PDF.
- Контроль переходов задач и технических актов.
- Разграничение доступа прораба, рабочего, инспектора и инвестора.
- Вход по паролю, JWT-защита, блокировка повторной первичной настройки и отзыв токена.
