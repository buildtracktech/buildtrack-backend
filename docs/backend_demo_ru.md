# Проверка BuildTrack Backend

Этот приёмочный сценарий проверяет только текущий этап backend: проекты, этапы, пользователи и
роли, задачи, нормативные правила, PDF-документы, проверки, замечания, отчёты и
технические акты. Он не демонстрирует дрон, облако точек, BIM/IFC, блокчейн,
дашборд или промышленную нормативную базу.

## 1. Запуск

```bash
python -m pip install -r requirements-dev.txt
alembic upgrade head
uvicorn app.main:app --port 8001
```

Открыть `http://127.0.0.1:8001/docs`. На новой базе один раз вызвать
`POST /auth/bootstrap`, затем получить токен через `POST /auth/login` и вставить его
в кнопку `Authorize`.

## 2. Автоматический сценарий

После применения миграций можно сразу подготовить весь сценарий одной командой:

```bash
python scripts/seed_acceptance_scenario.py
```

Скрипт скрыто запросит временный пароль и сам создаст проект, этап, четыре роли,
контрольные правила, исходный PDF, проверку, рассмотренные замечания, принятую
задачу и утверждённый технический акт. Итоговые ID будут записаны в
`output/acceptance/scenario-summary.json`, доступы - в защищённый локальный файл
`output/acceptance/access.txt`, а отчёт - в
`output/pdf/buildtrack-otchet-priemka-fundament.pdf`. Пошаговая проверка с точными
ID находится в `output/acceptance/how-to-check.txt`.

## 3. Исходный PDF отдельно

Создать безопасный синтетический файл:

```bash
python scripts/generate_demo_pdf.py
```

Результат появится в `output/pdf/buildtrack-primer-fundament.pdf`. В нём намеренно
нет поля `Ответственный проверяющий`, чтобы движок сформировал понятное замечание.
Файл помечен как приёмочный пример и не является проектной документацией для строительства.

## 4. Ручное создание данных через Swagger

1. Создать проект через `POST /projects/`.
2. Создать этап `Фундамент` через `POST /stages/`.
3. Создать прораба, инспектора, двух рабочих и инвестора через `POST /users`.
4. Добавить их в проект через `POST /projects/{project_id}/members` с ролями
   `project_manager`, `inspector`, `contractor`, `contractor`, `investor`.
5. По образцу `tests/fixtures/demo_normatives.json` создать три правила через
   `POST /normatives/`, заменив `stage_name_hint` на `stage_ids: [ID_ЭТАПА]`.
6. Загрузить сгенерированный PDF через `POST /documents/upload`.
7. Запустить `POST /checks/` для полученного `document_id`.

Ожидаемый результат проверки:

- правило `BT-TEST-001` находит поле `Этап`;
- правило `BT-TEST-002` находит поле `Редакция`;
- правило `BT-TEST-003` формирует замечание, потому что поля
  `Ответственный проверяющий` нет;
- итоговый verdict — `invalid`;
- дополнительно появляется отметка о необходимости экспертного подтверждения,
  потому что все учебные правила имеют технические признаки `is_demo=true` и
  `expert_validated=false`.

После проверки скачать JSON и PDF через `GET /checks/{check_id}/report` и
`GET /checks/{check_id}/report.pdf`.

## 5. Проверка ролей и задач

1. Авторизоваться как прораб и создать две задачи, назначив их разным рабочим.
2. Авторизоваться как первый рабочий: в `GET /tasks/` должна быть только его задача.
3. Перевести её `created -> active -> pending_verification`.
4. Попытка рабочего поставить `verified` должна вернуть HTTP 403.
5. Авторизоваться как прораб или инспектор и поставить `verified` либо `rejected`.
6. Авторизоваться как инвестор: задачи видны, но изменение возвращает HTTP 403.
7. Проверить неизменяемую историю через `GET /tasks/{task_id}/audit`.

## 6. Технический акт

После рассмотрения всех открытых замечаний создать акт через `POST /acts/` и
провести его `draft -> ready -> approved`. Утверждение выполняет прораб или
инспектор. Проверить снимки участников и замечаний, SHA-256 документа, хеш отчёта и
историю `GET /acts/{act_id}/audit`.

Это технический акт MVP, а не КС-2, не квалифицированная электронная подпись и не
платёжный документ.

## 7. Переход от временных учётных записей к реальным

Учебные пользователи не являются частью бизнес-логики. Системный администратор
может изменить ФИО, электронную почту и пароль через `PATCH /users/{user_id}` либо
создать отдельные реальные учётные записи через `POST /users`. После переноса ролей
старые учебные записи нужно деактивировать через `DELETE /users/{user_id}`.

Для боевых учётных записей заказчик должен передать ФИО, рабочие адреса электронной
почты и роли в каждом проекте. Пароли должны быть временными и заменяться владельцами
после первого входа.
